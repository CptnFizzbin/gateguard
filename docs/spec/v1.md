# KeyCard Policy Specification — Version 1

Status: Normative for `version: 1` policy documents.

This document is the authoritative definition of the v1 `PolicyDefinition`
format and its evaluation semantics. `SPEC.md` at the repository root remains
the informal overview/glossary; where the two disagree, this document wins.
It also serves as the conformance target for the JS (`impl/js`) and Java
(`impl/java`) implementations — a "Conformance notes" appendix at the bottom
records where each currently diverges from what's specified here.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

> **Revisions.**
> 1. Replaced the first draft's combining rule ("deny always overrides
>    allow, order is irrelevant") with CASL.js's own
>    **last-matching-rule-wins** semantics, restructured `rules` from two
>    separate `allow`/`deny` arrays into a single ordered, effect-tagged
>    list (order is now significant and MUST be preserved), replaced the
>    `"*"` wildcard token with the reserved names `anyAction`/`anySubject`,
>    and added an explicit console-diagnostic requirement for type issues.
> 2. Moved the optional `actions`/`subjects` catalogs under a new optional
>    top-level `meta` object, and — the more consequential change —
>    turned the wildcard tokens from fixed reserved words into
>    **policy-declared strings**: `meta.anyAction`/`meta.anySubject` name
>    *which* action/subject string, if any, this policy treats as a
>    wildcard. A policy that declares neither has no wildcard mechanism at
>    all; there is no longer a single hardcoded reserved word every policy
>    must avoid colliding with. See §2, §4, §5, §6.
> 3. Added `meta.customOperators`, a declarative catalog of the custom
>    `$`-prefixed condition operators a policy's rules use — the same
>    "advisory, not load-bearing" treatment as `meta.actions`/
>    `meta.subjects`, plus one new required diagnostic where a declared
>    operator turns out not to be registered at runtime. See §2, §7.4,
>    EC-17, EC-18, EC-21.
>
> See the Conformance notes appendix for what all of this means for the
> existing implementations.

## 1. Scope

KeyCard does not read or write policy files. An application (or a test, via
whatever YAML/JSON library it chooses) parses a document into a plain
`PolicyDefinition` value and hands it to `Policy.from(...)`. This spec
defines:

- The shape of a `PolicyDefinition` (§2) and its `version` field (§3).
- What an action and a subject are, and how they're matched, including the
  policy-declared wildcard tokens (§4, §5).
- The rule-evaluation algorithm — `can`/`cannot`/`require` (§6).
- The condition language and the evaluation semantics of every operator (§7).
- A catalogue of edge cases with their required behavior (§8).
- `append()` semantics, including how `meta` combines (§9).

It does not define the `PolicyBuilder` fluent API, wire format
(YAML vs. JSON), or any language-specific type system — those are
implementation concerns layered on top of this.

## 2. Document structure

```yaml
version: 1                          # required, integer, MUST be 1 for this spec
name: string                        # optional, informational only
description: string                 # optional, informational only

meta:                               # optional
  anyAction: string                 # optional — see §4
  anySubject: string                # optional — see §5
  actions: string[]                 # optional catalog — see §4
  subjects: string[]                # optional catalog — see §5
  customOperators: string[]         # optional catalog — see §7.4

rules:
  - [Effect, Action, Subject, Conditions?]
```

- `rules` MUST be present and MAY be an empty array. It is a single,
  **ordered** list — declaration order is significant (§6) and MUST be
  preserved by any parser or builder; an implementation MUST NOT treat
  `rules` as an unordered set.
- Each entry is a tuple of `[Effect, Action, Subject, Conditions?]`.
  `Effect` MUST be the literal string `"allow"` or `"deny"`. `Conditions`
  is optional; a three-element tuple `[Effect, Action, Subject]` is an
  unconditional rule.
- A rule tuple with a missing `Effect`, `Action`, or `Subject` (fewer than
  3 elements), or an `Effect` that isn't `"allow"`/`"deny"`, is malformed.
  Constructing a `Policy` from a definition containing a malformed rule
  tuple is implementation-defined (an implementation MAY throw at
  construction time, or MAY treat the rule as never-matching); it MUST NOT
  crash `can`/`cannot`/`require` at call time. Producing malformed tuples
  is a bug in the code that built the `PolicyDefinition` — not something
  `Policy.from` is responsible for repairing.
- `meta` is an entirely optional object grouping five independent,
  optional fields:
  - `meta.anyAction` / `meta.anySubject` — the wildcard tokens (§4, §5).
    A policy SHOULD declare whichever of these it actually relies on, and
    MAY omit both if it has no need for wildcard rules.
  - `meta.actions` / `meta.subjects` — declarative catalogs: the full set
    of action names and subject names this policy's rules use. A policy
    SHOULD include them — they're the closest thing v1 has to a schema,
    and let a reader (or a linter) see at a glance what a policy is
    actually about instead of having to enumerate every rule. See EC-18
    for what an implementation SHOULD do with them when present.
  - `meta.customOperators` — a declarative catalog of the custom
    `$`-prefixed condition operator names (e.g. `"$hasRole"`) this
    policy's rules use, in the same spirit as `meta.actions`/
    `meta.subjects`. **Declaring an operator here does not implement
    it** — a `PolicyDefinition` is data, not code, and cannot carry an
    executable checker. The operator's actual behavior still MUST be
    supplied separately, by the host application, through whatever
    runtime custom-condition-registration mechanism the implementation
    exposes (e.g. the JS `CustomConditionChecker` map passed to
    `Policy.from`). `meta.customOperators` exists purely so a reader (or
    linter) can see which custom operators a policy expects the host
    application to have registered, without hunting through every rule.
    See §7.4, EC-17, EC-18, EC-21 for how it interacts with the runtime
    registration.
  - When `meta.anyAction` is declared and any rule actually uses it, the
    `meta.actions` catalog (if also declared) SHOULD include that same
    token value as one of its entries — likewise for `meta.anySubject` and
    `meta.subjects`. (This document's own examples follow the convention
    of naming the token the same as the field itself —
    `meta.anyAction: anyAction` — but any string is a valid token; nothing
    requires that convention.)
  - Any of the five fields, or `meta` itself, may be absent; each is
    independent of the others.

## 3. Versioning

- `version` MUST be the literal integer `1` for a document evaluated under
  this spec.
- `Policy.from(definition)` (and any other policy-construction entry point)
  MUST reject a definition whose `version` is not one the implementation
  understands, by throwing a policy construction error. This is a
  forward-compatibility guard: a v1-only library reading a hypothetical v2+
  document MUST fail loudly at construction time rather than silently
  misinterpret rules it doesn't understand.
- `append(other)` MUST reject merging a definition whose `version` differs
  from the base policy's `version`, for the same reason.

(See the Conformance notes appendix — neither implementation currently
performs this check; it is a gap to close, not a description of existing
code.)

## 4. Actions

An action is a string naming what the caller wants to do (`Read`, `Create`,
`Update`, `MarkDone`, ...).

- Action matching is an exact, **case-sensitive** string comparison between
  the action passed to `can`/`cannot`/`require` and a rule's action.
- `meta.anyAction` (§2), if declared, names the one string that, when it
  appears in a rule's `Action` position, is a wildcard matching every
  action. There is no fixed, hardcoded wildcard word in this spec —
  whether any string is a wildcard, and which one, is entirely up to what
  (if anything) the policy declares in `meta.anyAction`. If `meta` or
  `meta.anyAction` is absent, this policy has **no** wildcard-action
  mechanism at all: every rule's `Action` is matched purely literally,
  including a rule that happens to use the string `"anyAction"` — with no
  `meta.anyAction` declared, that string carries no special meaning.
- Within a policy that *does* declare `meta.anyAction`, that exact string
  MUST NOT be used as an ordinary action name — a rule meaning the literal
  action equal to `meta.anyAction`'s value is indistinguishable from the
  wildcard, so don't declare a wildcard token that collides with a real
  action you also want to check for literally.
- There is no closed enum of valid actions required by this spec, but see
  §2: a policy SHOULD declare its full set via the optional `meta.actions`
  catalog. An action that never appears in any rule simply never
  matches — this is not an error by itself (see EC-18 for what an
  implementation SHOULD do when a catalog is present and a rule's action
  isn't in it).

## 5. Subjects

A subject has a **name** (its type, e.g. `Article`, `Comment`, `User`) and
optionally a **value** (a concrete instance's data, e.g.
`{ id: 1, owner_id: 1, status: "published" }`).

Three shapes may be passed to `can`/`cannot`/`require` as the subject:

| Passed as | Name | Value used for conditions |
|---|---|---|
| a bare string (`"Article"`) | the string itself | the string itself |
| a `SubjectDef` (type token, no instance) | `__name` | the `SubjectDef` token itself (see EC-11) |
| a `SubjectRef` (type token + wrapped instance) | `__name` | the wrapped instance |

- Subject-name matching is exact and **case-sensitive**, mirroring action
  matching.
- `meta.anySubject` (§2), if declared, names the one string that, when it
  appears in a rule's `Subject` position, is a wildcard matching every
  subject name — symmetric with `meta.anyAction` (§4) in every respect,
  including that its absence means no wildcard-subject mechanism exists
  for this policy, and that within a policy that does declare it, that
  exact string MUST NOT double as an ordinary subject name.
- As with actions, there is no closed enum of subject names required by
  this spec, but a policy SHOULD declare its full set via the optional
  `meta.subjects` catalog (§2). An unregistered name simply never matches
  (see EC-18).
- Checking a bare subject type (a string, or a `SubjectDef` with no
  instance data) against a rule that has field-based conditions is expected
  to fail those conditions (see EC-11) rather than skip them — there is no
  implicit "conditions don't apply when there's no instance" behavior.

## 6. Evaluation algorithm

KeyCard v1 follows CASL.js's own rule-combining semantics:
**the last matching rule wins.**

```
can(action, subject):
    name  = subjectName(subject)
    value = subjectValue(subject)
    for (effect, ruleAction, ruleSubject, ruleConditions) in reverse(rules):
        if matchesAction(action, ruleAction)
           and matchesSubject(name, ruleSubject)
           and (ruleConditions is absent or evaluate(value, ruleConditions)):
            return effect == "allow"
    return false   # nothing matched: default deny

cannot(action, subject):
    return not can(action, subject)

require(action, subject):
    if not can(action, subject): throw PolicyError

matchesAction(action, ruleAction):
    return action == ruleAction
        or (meta.anyAction is declared and ruleAction == meta.anyAction)

matchesSubject(name, ruleSubject):
    return name == ruleSubject
        or (meta.anySubject is declared and ruleSubject == meta.anySubject)
```

This fixes the properties that MUST hold for any v1-conformant
implementation:

1. **Default deny.** If the scan reaches the front of `rules` without a
   single match, the result is `false`. An empty policy (`rules: []`)
   denies everything.
2. **Last-matching-rule-wins.** An implementation MUST scan `rules` from
   the most-recently-declared entry backward to the first, and MUST return
   as soon as it finds one rule whose action, subject, and (if present)
   conditions all match. That rule's effect (`allow` or `deny`) *is* the
   answer — every earlier-declared rule, however specific or however
   unconditional, is irrelevant once a later-declared rule also matches.
   There is no independent "any deny beats any allow" veto and no
   AND-combination of multiple matching rules' effects: exactly one rule
   decides the outcome (or none does, and default deny applies).
3. **Order is significant, and MUST be preserved.** Because the algorithm
   is a reverse scan for the first match, the position of a rule relative
   to the others that could match the same action/subject is meaningful:
   moving a rule later in `rules` can change `can`'s answer for cases it
   overlaps with. An implementation, a builder, and a parser all MUST
   preserve declaration order end to end — see §2.
4. **Wildcard matching is policy-scoped.** `matchesAction`/`matchesSubject`
   consult *this policy's own* `meta.anyAction`/`meta.anySubject` (§4, §5);
   there is no global wildcard token independent of what a given policy
   declares. See §9 for what this means when two policies with different
   declarations are combined via `append`.

This is a deliberate alignment with CASL.js, which KeyCard's glossary cites
as an inspiration: broad rules are typically declared first, and later,
more specific rules override them for the cases they cover — including a
later `allow` reopening something an earlier `deny` closed, which was not
possible under this spec's first draft. Because only one rule ever decides
the outcome, authors relying on this model MUST order overriding rules
after the rules they're meant to override; see EC-3, EC-4, and EC-13 for
the practical consequences of this.

## 7. Conditions

A `Conditions` value filters *when* a rule applies, evaluated against the
subject's **value** (§5) — never against the subject's name.

### 7.1 Evaluation is total, and never throws

`evaluate(subject, condition)` MUST always return a boolean. It MUST NOT
throw for any well-formed `condition` value, regardless of what `subject`
is (including `undefined`/`null`, a primitive, or a shape the condition
doesn't expect). A condition that cannot be meaningfully evaluated against
the given subject evaluates to `false`, never to an error and never to
`true`. This is one of the two most important invariants for
cross-language consistency: it means a condition written for one subject
shape is safe to evaluate against a differently-shaped (or absent)
subject — it just won't match, and it will never crash the caller's
`can`/`cannot`/`require`.

The one place this is enforced by construction rather than by the
evaluator: if `ruleConditions` is entirely absent from a rule tuple, the
rule is unconditional and `evaluate` is never called for it (see §6).

**Type issues are diagnosed, not silenced.** A subset of the false results
above come from a genuine *type issue* — an operator receiving an operand
or a subject of the wrong shape for what it does (§7.4 marks exactly which
operators these are). When evaluation hits one of these, the implementation
MUST write a human-readable, error-level diagnostic to the console (or
equivalent host-language error/logger channel) identifying the operator and
what went wrong, so a policy author can find their mistake — but it still
MUST resolve that condition to `false` and SHOULD NOT throw an exception.
"Console error but no throw" is the required combination: silently
returning `false` with no diagnostic hides real authoring bugs (a `$gt`
compared against a string, an unparseable `$rgx` pattern) as if they were
ordinary non-matches; throwing would violate §7.1 and take down every
`can()` call that happens to hit the bad rule, for every request, until
someone reads a stack trace. A logged, non-fatal diagnostic gets the bug
noticed without making it load-bearing.

This diagnostic requirement is distinct from — and MUST NOT be conflated
with — an ordinary non-match that isn't a type issue: a missing field
(§7.3), an action/subject that simply doesn't match any rule, or an
unregistered custom `$op` (§7.4, EC-17) are not malformed input, so they
MUST NOT produce a console diagnostic on their own.

### 7.2 Bare-value shorthand

A condition that is itself a string, number, boolean, or `null` (not
wrapped in an operator object) is shorthand for `{ $eq: <that value> }`:

```yaml
{ status: archived }         # same as { status: { $eq: archived } }
```

### 7.3 Missing fields vs. explicit `null`

These are two different things and MUST be distinguished:

- **Missing field** — the subject is an object/map that does not have the
  key at all (or the subject isn't an object/map-like value in the first
  place). This makes the *entire field-condition* evaluate to `false`,
  regardless of which operator is nested inside it. `{ status: { $ne: "archived" } }`
  against a subject with no `status` key is `false`, not `true` — "not
  archived" requires a `status` that is present and isn't `"archived"`, not
  the absence of a `status`. See EC-6. This is absence, not a type issue —
  it MUST NOT trigger the §7.1 console diagnostic.
- **Explicit `null`** — the subject has the key, and its value is `null`.
  This is a real value and is compared like any other: `{ field: null }`
  (bare-value shorthand, §7.2) matches only when `subject.field` is
  `null`; `{ field: { $ne: null } }` matches when `subject.field` is
  present and is anything other than `null`.

`null` is never treated as a wildcard that matches anything.

### 7.4 Operators

Every operator below takes the *current* subject value at that point in the
condition tree (initially the subject's full value; narrowed by field
conditions, §7.5). The **Type issue** column marks which operators MUST
produce the §7.1 console diagnostic on a mismatch — an operator with `—`
in that column has no notion of a type mismatch; its non-matches are
ordinary logic, not diagnosable.

| Operator | Shape | Match when | On mismatch | Type issue (§7.1) |
|---|---|---|---|---|
| *(bare value)* | `string \| number \| boolean \| null` | `subject === value` (§7.2) | — | no |
| `$eq` | `{ $eq: value }` | `subject === value` | — (any two comparable values; unequal types are simply unequal) | no |
| `$ne` | `{ $ne: value }` | `subject !== value` | — | no |
| `$gt` / `$gte` / `$lt` / `$lte` | `{ $gt: number }` etc. | numeric comparison | `subject` and the operand MUST both be numbers; if either is not, `false` — never coerced, never a lexicographic/string comparison | **yes** |
| `$in` | `{ $in: value[] }` | `value` array contains `subject` | operand MUST be an array; otherwise `false` | **yes** |
| `$has` | `{ $has: value }` | `subject` array contains `value` | `subject` MUST be an array; otherwise `false` | **yes** |
| `$rgx` | `{ $rgx: string }` | the pattern is found *anywhere* in `String(subject)` (unanchored search, like `RegExp.prototype.test`, not a whole-string match) | an unparseable pattern string is `false`; a `null`/`undefined` subject is `false` | **yes**, for an unparseable pattern only — a `null`/`undefined` subject is an ordinary non-match, not a type issue |
| `$or` | `{ $or: Condition[] }` | at least one sub-condition matches (vacuously `false` for `$or: []`) | operand MUST be an array; otherwise `false` | **yes** |
| `$and` | `{ $and: Condition[] }` | every sub-condition matches (vacuously `true` for `$and: []`) | operand MUST be an array; otherwise `false` | **yes** |
| `$not` | `{ $not: Condition }` | the sub-condition does **not** match | — | no |
| *(field key)* | `{ fieldName: Condition }` | see §7.5 | see §7.3 | no (absence, not a type issue) |
| *(custom `$op`)* | `{ $op: value }`, registered via the implementation's custom-condition mechanism | delegates to the registered checker `(subject, value) => boolean` | an unregistered `$`-prefixed key is `false` | usually no (see EC-17) — **except** when `$op` is listed in `meta.customOperators` but no checker is actually registered for it at runtime, which MUST diagnose (see EC-21) |

`meta.customOperators` (§2) is a declarative catalog, not a registration
mechanism — it names which custom operators a policy expects, but the
checker function behind each one still MUST be supplied separately by the
host application at `Policy` construction time. Keeping the catalog, the
runtime-registered checkers, and what rules actually use in sync is
advisory in two directions and required in one:

- A rule uses `$op` and it's missing from `meta.customOperators` (when the
  catalog is declared): advisory only, same posture as EC-18.
- `meta.customOperators` lists `$op` but nothing was registered for it at
  runtime, and some rule actually reaches it during evaluation: this MUST
  produce the §7.1 console diagnostic (EC-21) — a declared-but-unfulfilled
  operator is exactly the kind of self-inconsistent setup that diagnostic
  exists to surface, distinct from simply never having declared or used
  the operator at all.

Numeric comparison uses IEEE-754 double semantics. Implementations SHOULD
ensure `NaN` never equals itself under `$eq`/`$ne` even where the host
language's default equality would say otherwise (e.g. Java's
`Double.equals` treats `NaN` as equal to `NaN`; that MUST NOT leak into
`$eq`/`$ne`/`$gt`-family behavior here).

`$rgx`'s pattern is always a search, not a full-string match — write `^...$`
explicitly when a whole-string match is intended. (This resolves a real
divergence between implementations; see the Conformance notes.)

### 7.5 Field conditions and multi-key objects

A condition object may contain more than one key. **Every key in a
condition object is evaluated, and the object matches only if all of them
do** — keys are implicitly ANDed together, whether they are operators,
field names, or a mix of both:

```yaml
{ $ne: null, status: "open" }   # subject is not null, AND subject.status == "open"
```

This applies uniformly: an operator key (`$eq`, `$gt`, `$or`, ...) does not
"consume" the whole object and does not cause sibling keys to be ignored.
(This resolves a real divergence between implementations — see the
Conformance notes: today's JS resolver returns as soon as it recognizes the
first operator key and silently drops any other keys in the same object;
that is a bug against this spec, not a documented feature. Do not rely on
operator-plus-field mixing being ignored.)

A key that does not start with `$` and is not a registered custom
condition is a **field condition**: it narrows the subject to
`subject[key]` and recursively evaluates the nested condition against that
narrowed value (§7.3 governs what happens when `key` is missing). Field
conditions may nest arbitrarily to reach into nested objects:
`{ author: { name: "Alice" } }` requires `subject.author.name === "Alice"`.

There is no dot-path or array-index syntax (e.g. `"author.name"` or
`"tags.0"`) in v1 — reach into nested structures only by nesting field
conditions as shown above. A field name that happens to contain a literal
`.` is matched as a single key, not split into a path.

`SPEC.md`'s glossary additionally lists a `{ $field: [key, Condition] }`
form as an alternate way to write a field condition. **`$field` is not part
of this spec and is not implemented by either implementation.** It is
reserved for a possible future version; a v1 condition MUST NOT rely on it,
and a `$field` key encountered today is handled like any other unrecognized
`$`-prefixed key — it is `false` unless a custom condition checker happens
to be registered under that exact name.

## 8. Edge case catalogue

Each entry states the required behavior and, where useful, the rationale.

- **EC-1 — Empty/absent rule list.** `rules: []` (or an absent `rules` key,
  depending on how strict the consuming implementation chooses to be per
  §2) means nothing is ever allowed; `can` is `false` for every
  action/subject.
- **EC-2 — No rule matches at all.** Same as EC-1: default deny. This is
  not a special case in the algorithm — it falls out of §6 naturally (the
  reverse scan returns `false` when it never finds a match).
- **EC-3 — Blanket deny, and being overridden.** A deny rule with no
  fourth tuple element blocks every instance of that action/subject
  combination — *as long as no rule declared after it also matches*. Under
  last-rule-wins (§6), a blanket deny is not immune to being reopened by a
  later, more specific `allow` for the same action/subject; if that's not
  the intent, the deny MUST be declared last among the rules it's meant to
  override.
- **EC-4 — Overlapping allow and deny, both conditional.** Each rule's own
  condition is evaluated independently against the same subject value, but
  only the *last-declared* rule among those whose conditions are satisfied
  decides the outcome (§6) — the two matching rules are not combined or
  ANDed together, and it is not enough for a deny rule to simply have a
  matching condition somewhere earlier in the list.
- **EC-5 — Wildcards.** Given `meta: { anyAction: anyAction, anySubject: anySubject }`,
  the rule `[allow, anyAction, anySubject]` (optionally with a condition)
  matches every action on every subject name; `[allow, anyAction, Article]`
  matches every action on `Article`; `[allow, Delete, anySubject]` matches
  `Delete` on every subject name. Wildcards are resolved purely by string
  comparison against whatever `meta.anyAction`/`meta.anySubject` declare
  (§4, §5) — they are not regex or glob patterns, and a policy that
  declares neither has no wildcard rules at all (a rule written as if
  `anyAction`/`anySubject` were always magic wildcards would, in such a
  policy, just be an ordinary — and almost certainly never-matching —
  literal action/subject name).
- **EC-6 — Missing field vs. explicit `null`.** See §7.3. A condition
  narrowed onto a field the subject doesn't have is `false`, including
  under `$ne`, `$not`, and `$or` — absence is not vacuous truth for
  "not equal" checks, and it does not trigger the §7.1 console diagnostic.
- **EC-7 — Checking a bare type with a conditional rule.** `can("Update",
  "Article")` (no instance data) against a rule
  `[allow, Update, Article, { owner_id: 1 }]` is `false` (assuming no
  later rule also matches) — the condition can't be satisfied without
  instance data to inspect, and that counts as "does not match," not as an
  error or an automatic pass. (Covered by existing fixture tests, e.g.
  `policy-01-simple.test.yaml`'s "denies Create on the bare Article type" —
  see the Conformance notes for how that fixture format maps onto this
  revision's schema.)
- **EC-8 — Unregistered action or subject name.** Any string other than
  the policy's own declared `meta.anyAction`/`meta.anySubject` (if any) is
  a legal action or subject to check. One that never appears in any rule
  simply never matches — there is no "unknown action" error by itself (see
  EC-18 when a catalog is declared).
- **EC-9 — Type issue inside a comparison, membership, or logical
  operator.** `$gt`/`$gte`/`$lt`/`$lte` against a non-numeric subject or
  operand, `$has` against a non-array subject, `$in`/`$or`/`$and` against a
  non-array operand: all resolve to `false`, and all MUST additionally
  produce the §7.1 console diagnostic — never a thrown type error (§7.1,
  §7.4).
- **EC-10 — Invalid regex pattern.** A `$rgx` pattern string that fails to
  compile in the host language's regex engine makes that condition `false`
  for every subject and MUST produce the §7.1 console diagnostic — not a
  thrown error. A malformed policy document should behave like an
  unsatisfiable rule with a logged warning, not crash every `can()` call
  that happens to hit it.
- **EC-11 — Evaluating conditions against a `SubjectDef` (no wrapped
  instance).** When `can`/`cannot`/`require` is passed a `SubjectDef` type
  token rather than a `SubjectRef`, the "subject value" used for condition
  evaluation is implementation-defined (today, the token object itself —
  see Conformance notes) but MUST NOT expose fields that make ordinary
  domain conditions (`owner_id`, `status`, etc.) accidentally match. A
  condition that inspects real domain fields is expected to evaluate to
  `false` in the absence of real instance data, the same as EC-7.
- **EC-12 — Vacuous `$or`/`$and`.** `{ $or: [] }` is always `false`
  (no alternative can be satisfied); `{ $and: [] }` is always `true`
  (there is no unsatisfied conjunct). This follows standard vacuous-truth
  conventions and both fall out of §7.4's table without needing a special
  case, but are called out because they're easy to get backwards. An empty
  array is a well-formed (if unusual) operand, not a type issue — no
  console diagnostic is warranted for `[]` specifically.
- **EC-13 — Duplicate or redundant-looking rules.** Under last-rule-wins
  (§6), listing two rules that could both match the same action, subject,
  and instance is **not harmless** the way it was in this spec's first
  draft — whichever of them is declared *later* in `rules` is the one that
  decides the outcome, full stop, even if an earlier rule looks more
  specific. This is a common CASL-style foot-gun: authors MUST place
  general rules first and any rule meant to override them strictly later
  in the array; reordering two overlapping rules can silently flip
  `can`'s answer.
- **EC-14 — `version` mismatch.** See §3: construction MUST be rejected
  (throw), both for `Policy.from` and for `append`, when the document's
  version isn't one the implementation understands.
- **EC-15 — Malformed rule tuple.** See §2: a rule tuple missing its
  effect, action, or subject element, or carrying an effect other than
  `"allow"`/`"deny"`, is implementation-defined at construction time, but
  MUST NOT be allowed to crash evaluation later.
- **EC-16 — Case sensitivity.** Action and subject-name matching (including
  against the `meta.anyAction`/`meta.anySubject` wildcards) is exact and
  case-sensitive: `"read"` does not match a rule written for `"Read"`, and
  if `meta.anyAction` is `"anyAction"`, the string `"AnyAction"` is not the
  wildcard. Field names inside conditions are likewise matched exactly as
  written.
- **EC-17 — Unregistered, undeclared custom condition operators.** A
  `$`-prefixed key that is neither a built-in operator (§7.4's table) nor
  registered as a custom condition checker on that `Policy`/
  `ConditionResolver` instance evaluates to `false`. It is never treated
  as a field name (field names MUST NOT start with `$` — see §7.5) and
  never silently ignored as a no-op `true`. When `meta.customOperators`
  either isn't declared or doesn't list this operator, this is not itself
  a type issue (§7.1) — an unrecognized operator name is a different
  mistake than a recognized operator given the wrong operand type — so it
  MUST NOT require the console diagnostic, though an implementation MAY
  still choose to log one (as a nicety, not a requirement) to help authors
  catch typos like `$eqq`. When the operator *is* listed in
  `meta.customOperators`, see EC-21 instead — declaring it changes the
  requirement from MAY to MUST.
- **EC-18 — A declared catalog doesn't cover a rule.** When a policy
  declares a `meta.actions`, `meta.subjects`, and/or `meta.customOperators`
  catalog (§2) and some rule's action isn't `meta.anyAction` and isn't
  listed in `meta.actions` (or, symmetrically, its subject isn't
  `meta.anySubject` and isn't listed in `meta.subjects`, or a custom `$op`
  it uses isn't listed in `meta.customOperators`), the implementation
  SHOULD produce a console diagnostic naming the offending rule and the
  undeclared name, but SHOULD NOT throw and MUST NOT change the rule's
  matching behavior — the rule still participates in evaluation exactly as
  if the catalog didn't exist. Catalogs are documentation and a lint
  signal, not a validation gate; this mirrors §7.1's "diagnose, don't
  fail" posture for type issues. (This is the "operator used but not
  cataloged" direction; EC-21 covers the opposite direction — an operator
  cataloged but never registered at runtime.)
- **EC-19 — Reserved wildcard names are policy-scoped, not global.**
  Unlike this spec's second draft, there is no single hardcoded wildcard
  word every policy must avoid. What's reserved is scoped to whatever a
  given policy declares: within a policy where `meta.anyAction` is set to
  some string, that exact string MUST NOT also be used as an ordinary,
  literal action name (and likewise for `meta.anySubject`/subjects) — see
  §4, §5. A *different* policy that declares no `meta.anyAction` at all,
  or declares a different token, is free to use that same string as an
  ordinary action name with no conflict, because reservation is scoped to
  the declaring policy, not global to this spec. `meta.anyAction` and
  `meta.anySubject` are independent of each other (one governs the
  `Action` position, the other the `Subject` position) and MAY even be set
  to the same literal string with no conflict, since actions and subjects
  are never compared against each other.
- **EC-20 — `append()` combining conflicting `meta`.** See §9: appending
  two definitions whose `meta.anyAction` (or `meta.anySubject`) values
  differ and are both declared MUST be rejected (throw) rather than
  silently picking one side — see §9 for the full rule and its rationale.
- **EC-21 — A cataloged custom operator is never registered.** When a
  policy declares `meta.customOperators` including `$op`, but the
  `Policy`/`ConditionResolver` instance evaluating it has no checker
  actually registered for `$op`, and some rule reaches `$op` during
  evaluation: the condition still resolves to `false` (§7.1, §7.4), but
  unlike the general "unrecognized operator" case (EC-17), this MUST
  produce the §7.1 console diagnostic and MUST NOT throw. The document
  promised `$op` would be meaningful; the application wiring didn't keep
  that promise, which is a genuine, worth-surfacing configuration bug —
  not merely undocumented vocabulary the way an uncataloged operator is.

## 9. `append()`

`policy.append(otherDefinition)` produces a new `Policy` whose `rules` list
is `this.rules ++ other.rules` — `other`'s rules are appended *after*
`this`'s, preserving each side's internal order. Because evaluation is now
order-sensitive (§6), this ordering choice is meaningful and MUST be
followed exactly this way: any rule from `other` that matches will be
considered more recently declared than, and therefore take precedence
over, a conflicting rule already present in `this` (last-rule-wins, §6
property 2). This makes `append` a natural way to layer an override policy
fragment (e.g. an admin-bypass policy) on top of a base policy — it is
**not** commutative (`a.append(b)` and `b.append(a)` can disagree on
overlapping rules), which is an intentional consequence of §6 and not a
bug. `append` MUST reject a version mismatch (EC-14 / §3) the same way
`Policy.from` does.

`meta` combines field by field:

- `actions`, `subjects`, and `customOperators` (the catalogs): the merged
  policy's catalog SHOULD be the union (with duplicates removed) of both
  sides' declared entries, or whichever side's list is present if only one
  side declares it. Since catalogs are advisory documentation (EC-18),
  there is nothing to conflict here.
- `anyAction` and `anySubject` (the wildcard tokens), independently: if
  only one side declares a given token, the merged policy MUST use that
  value. If **both** sides declare it and the values are **equal**, the
  merged policy MUST use that value. If both sides declare it with
  **different** values, `append` MUST be rejected (throw) — see EC-20.
  Silently preferring one side's token over the other's would change
  which rules from the *losing* side's original policy still act as
  wildcards after the merge, which is exactly the kind of silent
  behavior change this spec otherwise goes out of its way to avoid (§7.1,
  §3).

## Appendix: worked example

```yaml
version: 1
name: "Article Ownership Policy"
description: "Users can only modify their own articles"

meta:
  anyAction: anyAction
  anySubject: anySubject
  actions: [Read, Create, Update, Delete, anyAction]
  subjects: [Article, anySubject]
  customOperators: [$hasRole]

rules:
  - [allow, Read, Article]
  - [allow, Create, Article]
  - [allow, Update, Article, { owner_id: 1 }]
  - [allow, Delete, Article, { owner_id: 1 }]
  - [deny, Delete, Article, { status: archived }]
  - [allow, anyAction, Article, { $hasRole: admin }]
```

The final rule is declared last on purpose: because it's an `allow` and it
matches after the archived-article `deny`, an admin can still delete (or do
anything else to) any article regardless of the `deny` rule above it —
demonstrating last-rule-wins (§6) overriding an earlier blanket-looking
deny (EC-3). `$hasRole` isn't a built-in operator (§7.4) — it's a custom
one this policy declares in `meta.customOperators` and expects the host
application to have registered a checker for at `Policy` construction
time (e.g. one that checks `subject.roles.includes("admin")`); per EC-21,
if the application forgot to register it, evaluating this rule logs a
diagnostic rather than silently letting every admin-bypass check fail
closed with no clue why.

## Conformance notes (non-normative)

This section records where `impl/js` and `impl/java` currently diverge from
the spec above. It exists to guide follow-up fixes — it is not itself part
of the spec, and a future edit to either implementation should shrink this
list, not this document.

**This revision is a bigger lift than the last one.** The first draft of
this spec was reachable from both implementations with fairly small,
local fixes. Later revisions changed the document schema itself (one
ordered, effect-tagged `rules` list instead of separate `allow`/`deny`
arrays; an optional `meta` object holding the catalogs), the core
evaluation algorithm (reverse-scan last-match-wins instead of "any allow
AND NOT any deny"), and — most recently — turned the wildcard token from a
hardcoded `"*"` into a policy-declared string read from
`meta.anyAction`/`meta.anySubject`. Neither implementation, and none of the
existing YAML fixtures under `test/fixtures/policies/`, match this revision
yet — none of that is a description of current behavior; all of it is
follow-up work.

- **Schema: `rules.allow`/`rules.deny` → a single ordered `rules` list,
  plus a new optional `meta` object.** `impl/js/src/policy/PolicyDefinition.ts`'s
  `PolicyDefinition.rules` is currently `{ allow: [...], deny: [...] }`;
  `impl/java/.../policy/PolicyDefinition.java` holds the same split as
  `allowRules`/`denyRules`. Both need `rules` to become one ordered list of
  4-tuples (or equivalent) carrying an allow/deny effect per entry, and a
  new optional `meta` field (`anyAction`, `anySubject`, `actions`,
  `subjects`, `customOperators`). Helpfully, the JS `Rule` interface in that same file already
  has an `inverted: boolean` field per rule, and `PolicyBuilder.buildDef()`
  (`impl/js/src/builder/PolicyBuilder.ts`) already accumulates `this.rules`
  as one ordered array *before* splitting it into `allow`/`deny` at the
  end — the JS fix is largely to stop doing that last split and expose the
  ordered array with its `inverted` flags directly. The Java
  `PolicyDefinition.Rule` type has no such flag yet and needs one added,
  alongside collapsing `allowRules`/`denyRules` into one ordered `rules`
  list.
- **Algorithm: "allow AND NOT deny" → reverse-scan last-match-wins.**
  `impl/js/src/policy/Policy.ts`'s `checkPermission`/`matchesAnyRule` and
  `impl/java/.../policy/Policy.java`'s `checkPermission`/`matchesAnyRule`
  both currently OR-match `allow` and separately OR-match `deny`, then
  combine with "allow and not deny," independent of any ordering. Both
  need to change to a single reverse scan over the unified `rules` list
  that returns on the first (i.e., most-recently-declared) match, per §6.
- **Wildcard token: hardcoded `"*"` → `meta.anyAction`/`meta.anySubject`.**
  Both `matchesAction`/`matchesSubject` implementations currently treat
  the literal string `"*"` as the wildcard, unconditionally
  (`impl/js/src/policy/Policy.ts`, `impl/java/.../policy/Policy.java`).
  Both need to instead read the wildcard token, if any, from the
  `Policy`'s own `meta.anyAction`/`meta.anySubject` and fall back to "no
  wildcard" when unset, per §4/§6. This is a strictly bigger change than
  this spec's previous revision asked for (which still hardcoded
  `anyAction`/`anySubject` as fixed reserved words) — there is no fixed
  string to hardcode anymore.
- **No console diagnostics for type issues, in either implementation**
  (§7.1, EC-9, EC-10). Neither `ConditionResolver` implementation logs
  anything today — a `$gt` against a string, a non-array `$in` operand, or
  an unparseable `$rgx` pattern all just silently return `false`. Both need
  a console/log call added at each of the type-issue sites listed in
  §7.4's table.
- **`meta.customOperators` doesn't exist yet, and neither does the
  registered-vs-cataloged coverage check it implies** (§7.4, EC-17, EC-18,
  EC-21). The two implementations start from different places here: JS
  already has a runtime custom-checker registration point
  (`CustomConditionChecker`, `impl/js/src/conditions/Condition.ts`, passed
  to `Policy.from`), so its gap is purely additive — carry
  `meta.customOperators` through `PolicyDefinition`, then add the EC-21
  check (when evaluation hits a `$op` listed in `meta.customOperators`
  with no runtime checker registered for it, log the required diagnostic
  instead of falling through to the same silent `false` as any other
  unrecognized operator). `impl/java/.../conditions/ConditionResolver.java`
  has no custom-checker registration mechanism at all yet — that's a
  prerequisite there before `meta.customOperators` or EC-21 can mean
  anything on the Java side.
- **`version` is never validated** (§3 / EC-14). Neither `Policy.from`
  (`impl/js/src/policy/Policy.ts`) nor the `Policy` constructor
  (`impl/java/.../policy/Policy.java`) checks `definition.version`, and
  neither `append()` does either. Both need a version check added.
- **Missing field conflated with explicit `null`, in Java** (§7.3 / EC-6).
  `impl/java/.../conditions/ConditionResolver.java`'s top-of-method
  `if (condition == null) return true;` means a nested field condition
  whose *value* happens to be `null` (i.e. `{ field: null }`, or any
  operator wrapper — `{ field: { $ne: 5 } }` — recursing with a `null`
  condition) is mishandled at the object level, and separately, a
  `Map`-backed subject's *missing* key (`map.get(key)` returning `null`
  for an absent key) is indistinguishable from a *present* key whose value
  is `null`, unlike the reflection-based (POJO) subject path in the same
  class, which correctly treats a missing field as absence
  (`NoSuchFieldException` → `false`). The JS resolver
  (`impl/js/src/conditions/ConditionResolver.ts`) already matches this
  spec: it checks `key in subject` before descending.
- **`$rgx` is a full-string match in Java, a substring search in JS**
  (§7.4). `impl/java/.../conditions/stringConditions/StringConditions.java`
  uses `Pattern.matches(...)` (anchors the whole string); the JS resolver
  uses `RegExp.prototype.test`, which searches. This spec adopts the JS
  (search) behavior as normative (§7.4) since it already matches the
  informal `TValue.match(TSubject)` comment in `SPEC.md`; the Java side
  needs to switch to `Pattern.compile(...).matcher(subjectStr).find()`.
- **`$gt`/`$gte`/`$lt`/`$lte` are numeric-only in Java, native `>`/`<` in
  JS.** Java's `NumberConditions` already requires both operands to be
  `Number`; `impl/js/src/conditions/ConditionResolver.ts` does a bare `>`/
  `<` comparison, which for non-number operands falls back to JS's
  coercion/lexicographic rules instead of failing closed. The JS side
  needs a `typeof subject === "number" && typeof operand === "number"`
  guard added to match §7.4.
- **Mixing an operator key with sibling keys drops the siblings, in JS**
  (§7.5). `impl/js/src/conditions/ConditionResolver.ts` returns as soon as
  it matches one of the `if ("$xxx" in obj)` branches, so
  `{ $ne: null, status: "open" }` only ever evaluates `$ne` and silently
  ignores `status`. Java's loop-over-every-key structure in
  `ConditionResolver.java` already matches this spec's AND-everything
  rule. The JS resolver needs to be restructured to iterate every key in
  the condition object (as Java already does) rather than returning from
  inside a chain of single-key `if` checks.
- **`$rgx` on an invalid pattern throws in JS instead of evaluating to
  `false`** (EC-10). `new RegExp(obj.$rgx)` in
  `impl/js/src/conditions/ConditionResolver.ts` is not wrapped in a
  try/catch, so a malformed pattern string throws a `SyntaxError` out of
  `evaluate` instead of returning `false`. Java's
  `StringConditions.rgx` already catches and returns `false`. The JS side
  needs the same try/catch (and, per this revision, to also emit the
  console diagnostic once caught).
- **Existing YAML fixtures use the old `allow:`/`deny:` shape.** Every file
  under `test/fixtures/policies/*.yaml` (and the hand-authored example in
  `SPEC.md`) predates this revision and uses two separate `allow`/`deny`
  keys rather than one ordered, effect-tagged `rules` list plus `meta`.
  They'll need rewriting to the new shape as part of the implementation
  follow-up, not just a schema change in the two `Policy` classes.
